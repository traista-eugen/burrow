# Implementation plan

> **Status:** M0, M1 and M2 done. M3 is built; its "done when" is the user's everyday-use verdict. Last updated 2026-11-09.
>
> **Keeping this current:** tick items as they land, in the same commit as the code. If the scope of a milestone changes, edit it here and add an entry to [decisions.md](decisions.md) when the change is architectural.

The order is chosen to retire the biggest unknowns first:
1. Can we drive all four agents through one event model?
2. Does a durable flow engine hold up?
3. Only then: the GitHub flow, remote control and media.

Every milestone ends with something you can run.

## M0: Foundation ✅

- [x] Cargo workspace with `burrow-protocol`, `burrowd` and `burrow-app`
- [x] GPUI 0.2.2 window, with Burrow's own Windows manifest (D-010)
- [x] App icon, a black-and-tan dachshund, embedded in `burrow.exe`. Tray glyphs for `burrowd` are ready but nothing loads them yet. All are generated by `cargo xtask icons`.
- [x] Architecture, protocol, flow and decision documents (this folder)

## M1: Protocol and service skeleton ✅

- [x] **`burrow-protocol` types:** the JSON-RPC envelope, `initialize`, errors, `events/subscribe`, and the `index` stream events. Use serde with camelCase field names. Also `$/ping`, `$/cancel`, `events/unsubscribe` and the development-only `debug/append` (D-011).
- [x] **Schema export:** generate a JSON Schema with `schemars`, written to `schema/burrow-protocol.schema.json` by `cargo xtask schema`. A test fails if the file is out of date.
- [x] **`burrow-store`:** an SQLite event store (`rusqlite`, WAL mode) that appends and reads streams with gap-free sequence numbers. Database changes go through numbered migrations. Every commit is synced to disk (D-012).
- [x] **`burrowd` server:**
  - named pipe server (`tokio`), restricted to the current user, one `burrowd` per pipe;
  - one task per connection;
  - `initialize`, `$/ping` and `events/subscribe` with replay, through one store thread (D-014);
  - slow clients are disconnected and resume (D-015);
  - `debug/append`, accepted only with `--dev`, for the integration test.
- [x] **`burrow-transport`:** the pipe name and newline-delimited JSON framing, shared by `burrowd` and its clients (D-013).
- [x] **`burrow-client`:** connection handling plus typed calls, notifications, and subscriptions that resume after a reconnect. It runs on any executor (D-016).
- [x] **`burrowctl`:** `status`, `events tail <stream>`, and `debug append <stream> <event-json>`.
- [x] **Logging:** `burrowd` logs with `tracing` to `%LOCALAPPDATA%\Burrow\logs`.

**Done when** an integration test passes:
1. Start `burrowd`, subscribe to `index`, append events.
2. Kill and restart `burrowd`.
3. Resubscribe with the last seen `seq`: every event is received exactly once, in order.

✅ Passes: `events_survive_a_hard_kill_and_resume_exactly_once` in `crates/burrowd/tests/service.rs`. The same file covers replays racing with appends, two subscribers, `debug/append` refused without `--dev`, a second `burrowd` exiting, the handshake rules, disconnecting a client that stops reading, and the client on a non-tokio executor.

## M2: Agent sessions ✅

**Prerequisites** (all installed on the development machine):
- Node.js v24, which the npm ACP adapters need.
- The agent CLIs, logged in with subscriptions: Claude Code 2.1.319, Codex 0.167.0 and the Cursor CLI (`agent`) 2026.11.05.
- Muse Code.
- The pinned ACP adapters for Claude Code and Codex, installed by `burrowctl agent install claude|codex` into `%LOCALAPPDATA%\Burrow\agents` (D-024).

**Work:**
- [x] **Agent detection** (`agent/list`, `agent/refresh`): versions, login state, and models where cheap (Cursor's; replaced in M3 by the models of the agent's latest session, D-032). Read-only commands, run in Job Objects, cached (D-018).
- [x] **ACP adapter** (`burrow_agents::acp`) on the `burrow-acp` client (D-020, D-021):
  - [x] Cursor: `agent acp`
  - [x] Claude Code: `@agentclientprotocol/claude-agent-acp`
  - [x] Codex: `@agentclientprotocol/codex-acp`
  - The npm adapters are installed explicitly with `agent/install`, with no `npx` fallback; sessions start in the mode that asks before changes, and `agentMode` / `session/setAgentMode` choose another (D-024). A watchdog ends a turn that a cancel doesn't end and restarts the agent into the same session (D-025).
  - Tested through `burrowd` with the scripted fake ACP agent (`burrowd --dev`, agent `fake-acp`), and live against all three agents (`crates/burrowd/tests/acp_live.rs`).
- [x] **The adapter interface** (`burrow-agents`): `AgentAdapter`, `AgentSession`, `AgentEvent`; the ACP and MSP adapters plug into its `acp` and `msp` slots (D-018).
- [x] **A scripted fake agent** (`burrow-fake-agent`, a real process tree), offered with `burrowd --dev`: echo, permission requests, a simulated limit, slow turns.
- [x] **Session methods and events:** sessions are stored as `session:<id>` streams, with summaries on `index` and rows committed with them (D-017). Agent text is stored in chunks of about 100 ms. A restart marks live sessions `stopped`.
- [x] **Projects, kept minimal:** `project/add` (detecting the git `origin`), `list`, `get`, `remove`.
- [x] **Permission requests become inbox items**, answered through `inbox/respond`; answering twice is `conflict`.
- [x] **Job Objects** for every agent process, started suspended. Keep Windows awake while sessions are working.
- [x] **MSP adapter for Muse** (`muse serve`), in `burrow_agents::msp` on the `burrow-msp` client. Its types are written by hand and checked against the committed `muse schema` export (D-022). One `muse serve` per session, mapped onto Burrow's session events, approvals included (D-026). No user-input questions yet, and the sandbox stays on (D-027). Tests use `--provider echo` through `burrowd`, and replay a recorded approval; a live `meta` test passed on 2026-11-09.
- [x] **Limits:** detect usage limits and emit `limitReached`. `usage/get` uses Muse's `usage/read`, plus whatever the other agents report. No live limit has been seen yet: detection is tested with fixtures and the fake agents, so M7 should confirm it against a real limit.
  - Done in the core: `limitReached` and `AgentEvent::ProviderUsage` in the adapter interface, the `limited` state, prompts refused until `resetsAt`, `usage/get` and its types. Tested with the fake's simulated limit.
  - Done in the ACP adapter: Claude Code's, Codex's and Cursor's limits, detected by `burrow-acp`, become `limitReached` with `resetsAt` when the agent says; Claude Code's rate-limit status feeds `usage/get`. Tested with the fake ACP agent; no live limit was triggered.
  - Muse: done. Its quota failures become `limitReached`, and `usage/read` and `usage/changed` feed `usage/get` (D-026).
- [x] **Requests on their own tasks, and `$/cancel`** (D-019). **Clients check that the pipe's server runs as the current user.** Both were open from M1.
- [x] **`burrowctl session`:** `new` (`--agent-mode`), `list`, `prompt` (`--watch`), `watch`, `cancel`, `model`, `mode`, `stop`, `archive`; `inbox list|respond`; `project add|list`; `agent list|install`; `usage`. Readable text, or `--json`.

**Done when:**
- From `burrowctl`, each of the four agents can be prompted, its answer streams back, and a permission request can be approved from the inbox.
- Stopping a session leaves no stray processes, as checked by an automated test.

✅ The second passes, with the fake agent's real process tree: `stopping_a_session_leaves_no_stray_processes` in `crates/burrowd/tests/sessions.rs`. The same file covers streaming, the inbox, cancelling, the simulated limit, `$/cancel`, and a hard-killed `burrowd` taking its agents with it. `crates/burrowd/tests/acp.rs` does the same for ACP sessions, with the fake ACP agent.

The first passes for Claude Code, Codex and Cursor through `burrowd` and `burrow-client`: `crates/burrowd/tests/acp_live.rs` (run by hand on 2026-11-09) prompts each, streams the answer, approves a permission request with `inbox/respond`, and checks no process is left after `session/stop`. For Muse, `crates/burrowd/tests/muse.rs` covers prompting, streaming, cancelling and a clean stop with `echo`, and its live test approves a shell command from the inbox (D-027 says why that test turns Muse's sandbox off).

✅ The first also passes by hand from `burrowctl` (2026-11-09, against a separate `burrowd`). Each of the four agents answered "Reply with exactly: OK" with a streamed `OK`, asked before running `echo hi > hello.txt`, was approved with `burrowctl inbox respond`, created the file, and left no processes after `session stop`. Muse ran with `BURROW_MUSE_DISABLE_SANDBOX=1`, because its shell sandbox isn't set up on that machine (D-027).

## M3: Desktop app v1

- [x] **Connection:** the app connects through `burrow-client`, and starts `burrowd` if it isn't running. The client's I/O runs on `burrow_client::io_runtime()`, since GPUI doesn't run tokio (D-016). Reconnects resume every stream (D-029).
- [x] **Decide on `gpui-component`:** adopted, 0.9.1 on `gpui-pre` 0.3.12, with GPUI's manifest (D-028).
- [x] **Layout:** a sidebar with projects, sessions and runs (runs are empty for now), and an inbox panel (D-030).
- [x] **Session view:**
  - [x] **A virtualized transcript** (D-033): gpui-component's `MessageScroller` over `state::transcript::TranscriptModel`. It lays out only the rows on screen, follows new output while the reader is at the bottom, and offers "Jump to latest" when they scroll up. A long session opens at its end. An empty session says how to start.
  - [x] **Markdown that renders while it streams:** each answer's markdown state gets only its new text. Code blocks are highlighted with syntect and have a copy button, and text can be selected and copied. Thoughts collapse to one line.
  - [x] **Tool calls and diffs** (D-034): cards with the kind's icon, title, file and status, opening to diffs, command output or text. Runs of reads and searches collapse into one row. Diffs are unified, coloured, and numbered where the numbers are known.
  - [x] **The rest of a session's events:**
    - plans as a checklist updated in place;
    - permission requests with their answer, or why they expired (withdrawn by the agent, D-031);
    - turn ends with their reason, duration and usage;
    - limits as a banner with the reset time;
    - errors;
    - model and mode changes as one-liners.
  - [x] **Measured** (D-033): replaying 4,262 events costs 0.53 µs per event; scrolling them costs 1.2 ms a frame; a streamed chunk costs about 25 µs.
  - [x] **Fake agent scripts** for all of it: `/markdown`, `/diff`, `/tools`, `/long`, `/steps` and `/flood`.
  - [x] a prompt box: grows to six lines, then scrolls; Enter sends, Shift+Enter adds a line; Up in an empty box recalls the session's earlier prompts; disabled with the reason while starting, stopped or failed; a prompt sent during a turn, or before a limit resets, is refused in place with the reason, and the text is kept.
- [x] **Model picker and session state indicators.** The session header:
  - model and agent mode pickers from `Session.models` and `agentModes`, shown `name ?? id` and sent by id (D-032), modes with their descriptions;
  - a state pill (starting, ready, working, needs you, limited, stopped, failed) with what it means and the reason;
  - the latest turn's and the session's tokens and cost, where the agent reports them;
  - while `limited`, a banner with the reset time and a live countdown, from the session's `limit` or `usage/get`;
  - cancel, stop, archive (with a confirmation), rename inline, and open the folder in Explorer.
- [x] **The new session page and the sidebar:** the agent, a project or just a folder, the model and the agent mode up front; unavailable agents with their `problem`, and **Install** for a missing ACP adapter with its progress and errors; an available agent's note (Muse's sandbox). The sidebar's times redraw when one would change; its context menu opens, renames and archives; archived sessions hide behind a toggle.
- [x] **Startup time and memory checks** (D-036): `burrow.exe --measure <file>` and `cargo xtask measure`, on the release build with 50 fake sessions in the sidebar, 3 of them with 100 turns. Measured on 2026-11-09 (Ryzen 9 9950X, 64 GB, Radeon AI PRO R9700, Windows 11), median of 5 runs:

  | | `burrowd` running | the app starts `burrowd` |
  |---|---|---|
  | First frame, from process creation | 129 ms | 131 ms |
  | Connected | 141 ms | 201 ms |
  | Lists and agents loaded | 141 ms | 201 ms |
  | Working set / private bytes | 62 / 93 MB | 63 / 93 MB |

  With the 3 long sessions open as well, the basic transcript took 169 MB (about 36 MB per open session of about 1,400 events). Re-measured after the transcript rebuild (D-033) on the merged tree, 2026-11-09: first frame 128 ms with `burrowd` running and 130 ms when the app starts it; 62 MB working set with the sidebar alone; **72.6 MB working set, 101.7 MB private, with the 3 long sessions open (4,198 events)**, so about 3.5 MB per open long session. The target, under 300 ms to the first frame, is met. `burrow.exe` is 27.1 MB.
- [x] **The backend for the app** (additive protocol changes; see protocol.md's revision notes):
  - [x] **The sidebar:** sessions take their title from the first prompt, and `session/rename` changes it. `lastActivityAt` on `Session` and `SessionSummary` says when a turn last started or ended, and `session/list` returns the most recently active first. Every state or activity change is on the `index` as `entityStateChanged` with `lastActivityAt`, so the sidebar re-sorts without a `session/get`.
  - [x] **The mode picker:** Muse's approval modes are its agent modes, starting in `promptUnmatched` (D-031), so `session/setAgentMode` works for all four agents' modes. Cursor has modes but keeps its own default (D-024).
  - [x] **The inbox:** a permission request the agent withdraws expires at once, and the session goes back to `working`: ACP's `$/cancel_request`, and approvals Muse settles itself (D-031).
  - [x] **The model picker:** models are named by the ids sessions accept. `agent/list` reports the latest session's models where detection can't tell, and a model's name works in place of its id (D-032).
  - Tested with the fake agents (`/withdraw`, a parameterized `fake-param` model), a recorded Muse transcript, and Muse's echo provider.
  - [x] **The app's protocol gaps:** a session's `entityCreated` carries its agent and `inboxItemAdded` the item's actions, so the app no longer fetches each new entry; `AgentInfo.agentModes` lists the modes for picking one before the session starts (D-035).
- [x] **M2's follow-ups:** Muse's approval modes as agent modes; withdrawn permission requests; Cursor's model ids (`agent models` listed ids its sessions refuse); `burrowctl agent list` showing an available agent's `problem`, such as Muse's sandbox note.

**Done when** you prefer Burrow over the agents' own TUIs for everyday chats.

Everything above is built and was checked by eye on the merged release build (2026-11-09): the app starts against a `burrowd`, lists sessions, renders a fake session's plan, tool cards, collapsed reads, thoughts and highlighted code, scrolls with "Jump to latest", and replays a real Claude Code session from M2 (answer, shell tool card, approved permission, costs, stopped state) without duplicated text. What remains is the verdict, which only daily use can give.

## M4: Terminal sessions

- [x] **ConPTY**, called directly through `windows-sys` rather than `portable-pty`: `CreatePseudoConsole`, and `CreateProcessW` with `PROC_THREAD_ATTRIBUTE_JOB_LIST`, so the program is created inside its kill-on-close Job Object (D-038). **Terminal emulation in `burrowd`** with `alacritty_terminal` 0.26: one emulator per terminal, 10,000 lines of scrollback, fed by a reader thread that never waits for clients (D-039).
- [x] **Terminal sessions:** `session/create` with `mode: "terminal"` runs Claude Code's, Codex's, Cursor's and Muse's own TUIs, each the program its shim would run, with no `cmd.exe` or PowerShell in between; `burrowd --dev` adds a fake TUI (`burrow-fake-agent --tui`). `terminalOpened`, then `idle` while it runs, then `terminalClosed` with the exit code and `stopped` (code 0, or `session/stop`) or `failed`. Restarts mark them `stopped`.
- [x] **Terminal methods:** `terminal/attach` (snapshot), `terminal/update` (only what changed, at most every 16 ms per client, with `scrolled` counts and scrollback corrections, the next one only once the previous one is written), `terminal/input`, `terminal/resize`, `terminal/scrollback` (pages at negative indexes, in order with the client's updates), `terminal/detach`, `terminal/closed`; input modes, title and bell (D-039).
- [ ] **A GPUI terminal view**, drawn from cell runs.
- [x] **Decide terminal resize behaviour** when several clients are attached: the latest wins, the client that last resized or typed sets the size (Q7, D-040).
- [x] **`burrowctl terminal attach | show | send | scrollback`**, and `session new --mode terminal [--attach]`: a second client in any console, with Ctrl+] then `d` to detach.
- [x] **Tests** (`crates/burrowd/tests/terminals.rs`, the fake TUI on a real pseudo console, no quota): typing and colours; detaching and a second client seeing exactly the current screen; two clients at once; the resize rule; scrollback paging matching what scrolled; narrowing a terminal without duplicated lines; exits with their codes; stopping leaving no processes, `conhost.exe` included; a hard-killed `burrowd`; input modes; a client that stops reading never stalling the terminal or getting a backlog. The emulator's unit tests cover updates, scrolling, resets and paging.
- [x] **By hand** (2026-11-10, through `burrowctl terminal attach` in a console, against a separate `burrowd`): the first screens of Claude Code 2.1.319 and Cursor 2026.11.05 (their folder-trust questions), Codex 0.167.0 (its main screen) and Muse 1.4.15 (its workspace-trust question), unanswered, with no prompts sent; `session stop` left no process behind for any of them.

**Done when** any agent's TUI runs inside Burrow, and a second client can detach and attach without losing anything.

## M5: Flow engine core

- [ ] **Flow loader:** YAML, a flow JSON Schema, a validator, and MiniJinja templating.
- [ ] **Engine:**
  - a persisted state machine for runs and steps;
  - steps that wait (human, timer, event);
  - resuming after a restart.
- [ ] **Step kinds:** `agent`, `action: shell`, `human`, `run` (simple and RPC mode), `flow`. Add `script: lua` once a real flow needs it.
- [ ] **Control structures:** `needs`, `parallel`, `when`, `foreach`, `loop`, `retry`, `timeout`, `allowFailure`, `onFailure`, handlers.
- [ ] **Roles and picking a candidate.** Switching agents waits until M7.
- [ ] **Output caching** by input hash, and `run/rerunFrom`.
- [ ] **Dry runs** with fake agents and providers.
- [ ] **Run methods and events.** `burrowctl flow check | run | watch`.
- [ ] **A runs view in the desktop app:** the graph with live step states.

**Done when** a test flow finishes correctly even if `burrowd` is killed partway through. The test flow contains an agent step, a human approval, a Python custom step and a `foreach`.

## M6: GitHub and `deliver-issue`

- [ ] **A GitHub App setup guide** in `docs/github-app.md`, plus auth: App installation tokens for `burrow[bot]`, and your own token for actions you make yourself.
- [ ] **`IssueTracker` and `CodeHost` traits**, with GitHub implementations using `octocrab`.
- [ ] **Git operations** through the `git` CLI: worktrees, commits, pushes. `.burrow/` goes into `.git/info/exclude`.
- [ ] **Actions:**
  - [ ] `github.openPr`
  - [ ] `github.markReady`
  - [ ] `github.waitReview`
  - [ ] `github.merge`
- [ ] **Polling:** GitHub is polled using ETags. Webhooks come later, through the relay.
- [ ] **The `deliver-issue` flow and its prompts**, as drafted in `flows.md`.

**Done when** labelling an issue in a test repository ends in a merged PR, after one AI review round and one round of your review on GitHub.

## M7: Agent switching

- [ ] **Agents keep a progress checklist:** the agent prompts require `.burrow/progress.md`.
- [ ] **Handoff briefs:** generated, then given to the next candidate.
- [ ] **Switching rules:** `waitIfResetWithinMinutes`, the order of candidates, and skipping candidates that are limited or logged out.
- [ ] **Quota tracking per provider**, shown in the UI.
- [ ] **A way to simulate a usage limit** in tests.

**Done when:**
- A simulated limit in the middle of `implement` switches to the next agent, and the run still produces a working PR.
- A limit that resets soon makes the run wait instead.

## M8: Remote control

**Prerequisite:** Tailscale.

- [ ] **A WebSocket listener**, on the Tailscale interface only.
- [ ] **Pairing:** a QR code, Ed25519 device keys, the challenge/response login, and per-device permissions. Devices can be revoked.
- [ ] **A devices screen** in the desktop app.
- [ ] **The phone client.** Its technology isn't decided yet (Q2). First version: inbox, runs, sessions read-only, and answering inbox items.

**Done when:**
- A plan can be approved from the phone over Tailscale.
- A revoked phone is locked out immediately.

## M9: Creative flows

**Prerequisites:** ffmpeg, and accounts with the chosen media providers.

- [ ] **Media providers:**
  - ComfyUI, running locally on the R9700 (check AMD support first);
  - one cloud image provider;
  - one cloud video provider;
  - one text-to-speech provider.
- [ ] **`generate:` steps and ffmpeg actions.** Encoding uses the GPU (AMF) where possible.
- [ ] **A native media player spike in GPUI:** Windows Media Foundation, or ffmpeg/libmpv decoding into GPUI. This is the biggest risk in M9, so do it first.
- [ ] **The timeline format**, plus OpenTimelineIO export.
- [ ] **The `picture-book` flow.**
- [ ] **The `story-to-video` flow:** bible, narration first, animatic, then upgrading shots one by one.

**Done when** a 3-minute video renders from a premise, with storyboard approval, and editing one scene re-renders only that scene.
